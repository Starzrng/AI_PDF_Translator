# Харнесс: как устроен и куда растёт

**Харнесс** — всё, что окружает агента и превращает «переведи этот PDF» в повторяемый цикл с проверяемыми шагами. Модель-переводчик одна и та же; качество результата и количество ручных вмешательств определяет обвязка вокруг неё:

| Часть | Что это здесь | Где |
|---|---|---|
| **Правила** | что делать и в каком порядке, жёсткие запреты | `AGENTS.md`, `docs/translation-conventions.md` |
| **Инструменты** (действия) | команды, которые агент запускает вместо ручной вёрстки | `python -m pdft inspect / init / build / review` |
| **Датчики** (обратная связь) | автопроверки, которые говорят агенту, что не так, без человека | `pdft/qa.py` → `out/qa.json` |
| **Память** | уже принятые решения: переводы, термины, запреты | память переводов (`pdft/tm.py`), `docs/glossary/` |
| **Контрольные точки человека** | где решение остаётся за пользователем | пилот, спорные термины, итоговая постраничная вычитка |

Главный принцип: **каждое повторяющееся вмешательство пользователя превращается в правило, данные или датчик.** Агент без контекста не помнит, что вы поправили в прошлый раз, — но прочитает правило, возьмёт перевод из памяти и получит ошибку от проверки.

## Цикл оверлей-работы

```
inspect ─► init ─► перевод TODO ─► build ─► QA ── ошибки/предупреждения ──┐
                        ▲                     │                            │
                        └──── правка ◄────────┘◄───────────────────────────┘
                                              │ 0 ошибок
                                              ▼
                                   review (пары PNG) ─► пользователь
```

- `inspect` — разведка: шрифты (subset → перевод в Arial), растр ниже 200 dpi (кандидаты на перерисовку), векторные схемы, сколько абзацев найдётся в памяти переводов.
- `init` — каркас `translations.py`: строки склеены в абзацы (`merge`), блоки из нескольких ячеек разделены (`P3b10.1`), у каждого абзаца — английский оригинал с разметкой выделений (`<b>`, цвет) и перевод из памяти, если он есть.
- `build` — сборка: исходный текст удаляется (графика и картинки не трогаются), перевод вписывается; если текст не помещается, блок растёт в свободный фон (вниз для абзацев, влево для подписей, прижатых к выноске справа, в обе стороны для ячеек), а не сжимается. Сразу после сборки — QA.
- `review` — пары «оригинал | перевод» для глаз агента и пользователя.

## Слабые места → ответ харнесса

| Проблема (со слов пользователя, 2026-10-27) | Что сделано | Статус |
|---|---|---|
| Термины, кривые фразы | память переводов из прошлых работ; запреты в `docs/glossary/style-rules.json` → ошибка `style` | частично: нет глоссария-как-данных для терминов работы, нет вычитки стиля |
| Подложка налезает на графику | исходный текст удаляется, белая подложка не рисуется; датчики `text-art`, `fill-art` по рендеру «только графика» | сделано |
| Текст слипся, полстраницы пусто | рост блока в свободный фон вместо сжатия; датчик `shrunk` | сделано для отдельного блока; перекомпоновки всей страницы нет |
| Некачественная графика не перерисовывается | `inspect` находит растр < 200 dpi | только обнаружение; перерисовки нет |
| Абзацы разрезаны на строки | склейка в `segments.py` | сделано |

## Что дальше (по ценности)

1. **Глоссарий работы как данные** — термины EN→RU, которые `qa` проверяет в каждом абзаце (сейчас термины только в markdown и в голове агента).
2. **Текст внутри картинок** — OCR скриншотов и схем: найти запечённый текст, решить «оставить / заменить / перерисовать», для перерисовки — конвейер как в XM-100.
3. **Перекомпоновка страницы** — когда одному блоку не хватает места, сдвигать соседние блоки (сейчас только рост в свободный фон).
4. **Перевод через API** — `init` → черновой перевод моделью с правилами и памятью в промпте → агент-редактор → QA. Шаг к сервису.
5. **Шрифт ближе к оригиналу** — полный HarmonyOS Sans (с кириллицей) вместо Arial для Creality.
